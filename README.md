# 서울 크레센도 (Seoul Crescendo)

**지금 갈 수 있고 아직 붐비지 않는 곳으로 짜는 서울 반나절 일정**

서울을 찾은 외국인 관광객이 겪는 가장 흔한 실패는 코스가 시시한 것이 아니라
**갔는데 없는 것**이다. 이미 끝난 축제, 오늘 문을 닫은 가게, 비가 와서 못 하게
된 야외 일정. 여기에 하나가 더 있다 — **가 보니 사람만 너무 많은 것.**

비짓서울 API의 관광 콘텐츠에 두 계층을 얹는다. 하나는 *지금 갈 수 있는가*를
판정하는 계층이고, 다른 하나는 *요즘 뜨는가*와 *지금 붐비는가*를 **합치지 않고
따로 재는** 계층이다. 통과한 것만으로 시간표가 있는 반나절 일정을 만든다.

이름이 곧 방법이다. 크레센도는 *아직 크지 않은데 커지는 중*이라는 뜻 하나뿐이고,
이미 붐비는 곳은 포르테다.

```
내 위치            →  마포구 서교동 · 주변 186곳
10:00부터 4시간
맑음 21°C

10:16–11:46  2027 S/S 서울패션위크   3일 뒤 끝납니다. 지금 아니면 놓칩니다
   ↓ 도보 6분 (추정)
11:53–12:53  뿌자2 인도 할랄 음식점   11:53 도착이면 식사 시간에 맞습니다
   ↓ 도보 4분
12:56–13:41  동대문 쇼핑타운
플랜 B  광화시장 — 날씨가 바뀌면 여기로
```

화면과 대화형 도우미가 한국어·영어로 돈다. 실행은 [빠른 시작](#빠른-시작),
배포는 [DEPLOY.md](DEPLOY.md).

## 아키텍처

### 파이프라인 — 무거운 일은 미리, 요청은 가볍게

```
 비짓서울 API ─┐
               │  ┌─────────┐   ┌───────────┐   ┌────────┐
 유동인구      ├─▶│ collect │──▶│ normalize │──▶│ index  │  ← 서버 시작 시 1회
 위키 조회수   │  └─────────┘   └───────────┘   └────────┘
 위성 LST/NDVI ┘   data/raw/      구조화 시간표     3,802건 적재 (약 200ms)
                   *.jsonl.gz     실내외 태깅       행정동 매칭 · 번역 병합
                                                        │
     ┌──────────────────────────────────────────────────┘
     │  ┌──────────┐   ┌─────────┐   ┌────────┐   ┌────────┐
     └─▶│ validate │──▶│ quality │──▶│ course │──▶│ server │──▶ 화면
        └──────────┘   └─────────┘   └────────┘   └────────┘
         통과/탈락/       일곱 축         시간표 있는    FastAPI
         판정불가         랭킹            반나절 일정
              ▲              ▲                ▲
              │              │                │
          기상청 실황   모멘텀 · 실시간 혼잡   경로 실측(TMAP/ODsay)
```

**정규화·행정동 매칭·인기도는 적재 시점에 한 번만 한다.** 요청마다 다시
파싱하던 초기 구현은 판정 한 번에 120ms, `/api/candidates`에 600ms가 들었다.
지금은 일정 하나가 67ms다.

### 런타임 — 정적 화면과 상주 API를 나눈다

```
 브라우저 ──┬─▶ Vercel (정적)      index.html · app.js · style.css
            │                      행정동 경계 GeoJSON · 위성 열지도 JSON
            │
            └─▶ /api/*  ─rewrite─▶ Render (FastAPI 상주 프로세스)
                                    3,802건 인덱스 · 경로/인기도 캐시를
                                    메모리에 얹고 산다
```

런타임이 geopandas·shapely·pyproj까지 162MB라 서버리스 함수 한도를 넘고,
무엇보다 **캐시가 성능의 전부**라 요청마다 새로 뜨는 실행 모델이 맞지 않는다.
그래서 화면은 정적 호스팅, API는 상주 프로세스로 나눴다.

### 계층별로 하는 일

| 모듈 | 하는 일 | 이 계층의 원칙 |
|---|---|---|
| `collect` | 목록 → 상세를 건건이 받아 `data/raw`에 쌓는다 | `cid` 기준 재개 가능. 목록 응답에 좌표·기간·운영시간이 없어 사전 배치가 필수다 |
| `normalize` | 자유 문장 운영시간 → 요일별 시간표, 실내외 태깅 | **실패를 숨기지 않는다.** `high`/`low`/`none` 세 단계로 남긴다 |
| `index` | 적재 시점 1회 정규화 + 행정동 매칭 + 다국어 병합 | 요청 경로에서 파싱을 없앤다 |
| `validate` | 기간 → 날씨 → 운영 순으로 거른다 | **탈락과 판정 불가를 구분한다.** 모르는 것을 '열렸다'로 하면 헛걸음, '닫혔다'로 하면 멀쩡한 곳이 사라진다 |
| `momentum` | 시계열 → 수준·모멘텀·급등 | 자료의 뜻을 모른다. 소스는 함수 하나로 꽂는다 |
| `crowd` | 실시간 혼잡·인구·예보 | 관측 지역 800m 밖에는 값을 쓰지 않는다 |
| `quality` | 일곱 축 랭킹 + 다양성 상한 | 가중치와 근거 문장을 화면에 그대로 내보낸다 |
| `course` | 도착 시각으로 다시 판정하며 일정을 쌓는다 | '지금 열림'이 아니라 **'도착할 때 열림'**을 본다 |
| `agent` | 도구를 확정적으로 돌리고 LLM은 서술만 | 모델이 장소를 지어낼 수 없다 |

자세한 설계 판단은 [ARCHITECTURE.md](ARCHITECTURE.md), 문서에 적힌 숫자가
어느 코드에서 나왔는지는 [docs/수치_출처.md](docs/수치_출처.md).

### 어디에 어떻게 쓰는가

**비짓서울 API** — 전 카테고리(문화관광·역사관광·자연관광·체험관광·쇼핑·음식·
숙박·축제)를 전수 수집해 서비스의 콘텐츠 기반으로 삼는다. 목록 응답에는 좌표도
기간도 운영시간도 없어서 **상세를 건건이** 받아야 하고, 그래서 실시간 호출이
아니라 사전 배치다. 한·영·일 필드를 그대로 병합해 어권별 화면에 쓴다.

**외국인 유동인구** — 관심이 아니라 **방문**이다. 2023년 1월 이후 43개월을
쓴다(2017~2022는 연 단위 묶음이라 무겁고, 전년 동월비에는 43개월로 충분하다).
시간대별로 그냥 합치면 가장 붐비는 시각이 새벽 1·2시로 나온다 — 생활인구는
'그 자리에 있는 사람'이라 새벽에는 숙소 인구가 잡힌다. **낮 11~18시만 센다.**

**실시간 도시데이터** — 관측 지역 반경 800m 안에 우리 콘텐츠의 77.0%(2,856건)가
든다. 그 밖은 값을 쓰지 않는다. 비거주 비율이 특히 값진데, 붐비는 것이
출퇴근 인파인지 관광 인파인지 갈라 주기 때문이다.

**위성** — 기상청은 서울에 대푯값 하나를 준다. 실제 지표는 같은 시각 같은 도시
안에서 31.4°C부터 46.3°C까지 벌어진다. 여름 한낮 장면 여러 장(Landsat 6·
Sentinel 4)을 중앙값 합성해 행정동 426개로 집계한다.

**경로** — 후보를 고르는 동안에는 추정만 쓰고, 확정된 서넛만 동시에 물어
실측으로 바꾼다. 구간마다 **실측인지 추정인지**가 화면에 표시된다.

### 키가 없으면 무엇으로 떨어지나

**하나도 없어도 전부 동작한다.** 없으면 무엇으로 떨어지는지는 `/api/health`와
화면에 항상 표시된다. `.env.example` 참고.

| 변수 | 없을 때 |
|---|---|
| `VISITSEOUL_API_KEY` | 공개 카탈로그를 소스로 수집 |
| `SEOUL_RTD_KEY` | 혼잡 축이 중립(0.5)으로 빠지고 순위에 영향을 주지 않는다 |
| `KMA_API_KEY` | 맑음 21°C 기본값으로 판정 (허브·포털 키 모두 받는다) |
| `TMAP_APP_KEY` | **공개 OSRM 보행 프로파일로 실측** (그것도 막히면 직선 × 국소 우회율) |
| `ODSAY_API_KEY` | 대중교통 시간을 평균속도로 추정 (도메인 등록 + `ODSAY_REFERER` 필요) |
| `NAVER_CLIENT_ID`/`SECRET` | 자동차 시간을 직선거리로 추정 |
| `KAKAO_REST_KEY` | 카카오 등재 확인을 건너뜀 |
| `GOOGLE_PLACES_KEY` | 평점 없이 위키 조회수만 |
| `ANTHROPIC_API_KEY` 또는 `GEMINI_API_KEY` | 규칙 기반 의도 파악·템플릿 답변 |

도보만은 키가 없어도 실측을 준다. OSM 도로망 위에서 도는 공개 OSRM 보행
프로파일이 있어서다. 덕수궁→명동성당을 직선 추정은 1,430m/21분, OSRM은
1,443m/19분으로 답한다. 값은 비슷해도 하나는 잰 값이고 하나는 가정한 값이다.

### 쓰지 않는 것

| | 왜 |
|---|---|
| 구글 Places 평점·리뷰 수 | `rating`이 Enterprise SKU라 유료다. 현재 `data/popularity.json`의 구글 평점·리뷰는 **0건**이고, 품질 하한 게이트는 `ratings.py`의 **합성값**으로 돈다. 화면에 내보내지 않으며 산출 파일에 `synthetic: true`가 박힌다 |
| 카카오맵 평점 | 로컬 API는 이름·주소·좌표·카테고리만 준다. 평점은 웹에만 있고 크롤링은 약관 위반 |
| 네이버 데이터랩 소비 | 소스는 꽂혀 있으나 12개월뿐이라 전년 동월비를 낼 수 없다. 엔진이 산출을 거부하고 쓰지 않는다 |
| 국적별 취향 추정 | 같은 나라 사람도 취향은 제각각이고, 국적으로 사람을 분류하는 화면은 좋게 읽히지 않는다. 대신 여행 스타일을 본인이 고른다 |

## 빠른 시작

```bash
pip install -r requirements.txt

python -m weatherfit.collect --all            # 콘텐츠 수집 (약 20분)
python -m weatherfit.collect --all --lang en  # 영어판 (선택)
python -m weatherfit.popularity build         # 인기도 캐시 (약 25분, 선택)
python -m weatherfit.popularity verify        # 오매칭 걸러내기 (약 1분)
python -m weatherfit.server                   # http://127.0.0.1:8020
```

행정동 경계와 수집본(`data/raw/*.jsonl.gz`, 5.0MB)이 저장소에 들어 있어
클론하고 서버만 띄우면 바로 돈다. 수집·인기도·위성 단계는 근거를 재현하고
싶을 때만 돌리면 된다.

배포는 [DEPLOY.md](DEPLOY.md) — 프런트 Vercel, API Render.

## 무엇으로 고르는가

거리만 보면 약국이 오고, 품질만 보면 반대편 동네 명소가 온다. 인기만 보면
유명한 곳만 돌게 되고, 취향만 보면 늘 같은 것만 본다. 일곱을 섞는다.

| 축 | 비중 | 무엇을 보나 |
|---|---:|---|
| 가까움 | 24% | 2km를 0점 기준으로 한 근접도 |
| 정보 충실 | 18% | 설명 길이·태그·홈페이지·무장애 정보·운영시간 신뢰도 |
| 알려진 곳 | 14% | 위키백과 문서 유무와 월별 조회수 — **지금의 크기** |
| 요즘 뜨는 | 12% | 그 크기가 커지고 있는가 — **지금의 변화** |
| 덜 붐빔 | 12% | 실시간 혼잡도 4단계. 모르면 중립 |
| 취향 일치 | 12% | 말한 관심사 · 좋아요 · 관심없음으로 학습한 태그 벡터 |
| 여행 스타일 | 8% | 고른 스타일과 VITALITY 5축의 맞음 |

점수는 화면에 그대로 적힌다. *"덜 붐빔 12% — 여유 · 지금 500~600명 ·
외지인 51% · 15:00 이후 여유"*. 왜 뽑혔는지 감추면 고쳐 달라고 말할 수도 없다.

여기에 **다양성 상한**을 건다. 반나절에 식당 네 곳은 일정이 아니다.
대분류 최대 2곳, 소분류 최대 1곳. 약국·편의점·관광안내소·물품보관소는
일정에서 빼되 주변 목록에는 남긴다 — 약이 필요한 순간도 있다.

## 뜨는 것과 붐비는 것은 다르다

리뷰순·평점순은 **크기**를 보여 준다. 크기를 알아도 **움직임**은 알 수 없다.
외국인 방문량 상위 16개 행정동의 전년 동월비가 −17.6%에서 +64.6%까지
흩어지고, 1위 명동은 +2.9%로 멈춰 있다. 크기와 움직임의 상관은 r = +0.14다.

그래서 시계열을 받아 세 축으로 **쪼개고 합치지 않는다.**

| 축 | 무엇을 재나 | 계산 |
|---|---|---|
| 수준 | 지금 얼마나 큰가 | 최근 12개월 합 |
| 모멘텀 | 작년 같은 달보다 늘었나 | 전년 **동월**비 |
| 급등 | 제 이력보다 최근이 튀었나 | 최근 3개월 z점수 |

전년 **동월**과 견주는 게 요점이다. 관광은 계절성이 지배적이라 전월과 비교하면
"여름에 한강이 뜬다"가 트렌드로 잡힌다. 여기에 두 보정을 건다. **시장 효과
제거** — 전년비에서 그 소스 전체의 중앙값을 뺀다(변이할당분석). **크기 보정** —
셈 자료에는 분산 안정화 변환 `A(x)=2√(x+3/8)`을 적용해 월 1건짜리와 500건짜리를
같은 자에 올린다.

**엔진은 자료의 뜻을 모른다.** `axes(values, period, scale)`은 숫자만 받고,
소스는 함수 하나로 등록한다. 위키백과 조회수, 행정동 외국인 유동인구, 소비
데이터가 같은 엔진에 꽂힌다. 유행이 바뀌어도 모듈은 남는다.

### 관심과 방문은 다른 것을 말한다

민간 지도가 보여 주는 리뷰·검색·저장은 전부 **관심** 신호다. 그 자리에 실제로
있던 사람 수는 서울시 행정동 단위 단기체류 외국인 생활인구(OA-14993)에만 있다.
108개 장소에서 둘을 맞대 보면 **상관계수 +0.014** — 사실상 무관하다.

| | 관심(조회수) | 방문(유동인구) | |
|---|---:|---:|---|
| 효창공원 | −26.6% | **+50.0%** | 이미 아는 곳이라 검색하지 않는다 |
| 광화문광장 | **+185.9%** | −2.7% | 화제만 되고 발길은 없다 |

조회수만 보면 앞의 무리는 추천에서 사라진다. 두 축을 나눠 뒀기에 살아남는다.

### 지금 붐비는가

서울시 실시간 도시데이터로 121곳의 혼잡도(4단계)·실시간 인구·비거주 비율·
12시간 예보를 5~10분 주기로 받는다. 관측 지역 반경 800m 안에 우리 콘텐츠의
**77.0%(2,856건)**가 든다. 800m를 넘으면 값을 쓰지 않는다 — 남의 동네 혼잡을
이 자리의 혼잡이라 말하면 안 된다.

혼잡과 모멘텀의 상관은 **r = +0.146(결정계수 0.021)**이다. 추세를 알아도 지금
붐비는지는 알 수 없다는 뜻이고, 그래서 두 축이 사분면을 만든다. 관측 119곳 중
**14곳이 '뜨는데 아직 안 붐빔'**, **17곳이 '이미 붐비는데 더 뜸'**이었다.
앞쪽은 안내하고 뒤쪽은 숫자로 알린다.

가라 마라를 정해 주지는 않는다. 지금 몇 명이 있고 언제 여유해지는지를 말하면
판단은 각자가 한다 — 붐비는 곳을 굳이 찾아가는 이유도 사람마다 다르다.

  11~18시만 세도록 고쳤다.

## 화면과 도우미가 영어로 돈다

외국인이 쓸 서비스라 화면·판정 사유·근거·챗봇이 전부 영어로 돈다. 다만
**비짓서울 원문은 손대지 않는다** — 영업시간 원문을 어설프게 옮기면 없는 정보를
만든다. 경계에서만 옮기고, 표에 없는 한국어는 지우지 않고 그대로 남긴다.
조용히 사라지는 것보다 남아 있는 편이 고치기 쉽다.

짧은 낱말이 문장 가운데를 자르는 사고가 반복돼서, 세 글자 이하 키에는 앞뒤가
한글이면 건너뛰는 경계를 걸었다. `도보`가 `듣도보도못한말` 안에서 잡혀
`듣Walk도못한말`이 됐고, `붐빔`이 `붐빔은`에서 잡혀 `Crowded은`이 됐다.
단위는 숫자가 앞에 붙을 때만 바꾸고 구절보다 **먼저** 처리한다 — 구절 표가
`조회`를 먼저 지우면 `588회 조회`를 한 덩어리로 볼 기회가 사라진다.

서버 표와 화면 표가 갈라지지 않게 테스트로 묶어 두었다.

## 위성으로 만드는 골목 단위 더위 지도

기상청은 서울에 대푯값 하나를 준다. 오늘 서울 33°C. 그런데 실제 지표는 같은
시각 같은 도시 안에서 **31.4°C부터 46.3°C까지** 벌어진다.

| 행정동 | 지표면온도 | NDVI | |
|---|---:|---:|---|
| 종로구 창신1동 | 46.3°C | 0.09 | 밀집 저층, 녹지 없음 |
| 용산구 청파동 | 46.3°C | 0.09 | |
| 중구 을지로동 | 45.9°C | 0.07 | |
| … | | | |
| 도봉구 도봉1동 | 32.1°C | 0.54 | 북한산 자락 |
| 강북구 우이동 | 32.1°C | 0.53 | |

이 14.9도 차이는 지상 관측망으로는 못 만든다. 관측소는 서울에 몇 곳뿐이고 그
사이를 보간해 봐야 골목이 나오지 않는다. **위성은 30m 격자로 도시 전체를 한
번에 찍는다.**

날씨에 맞는 곳을 고르는 서비스가 날씨를 도시 하나로 뭉뚱그리면 이런 일이
생긴다. 35°C 판정에서 **실외 후보가 0건**이었다 — 서울 어디든 실내로 가라는
답이다. 위성 열지도를 보게 하니 173건이 살아남았고, 그 목록이 청운효자동 ·
여의동 · 상암동 · 잠실2동 · 우이동이다. 서울 사람이 더운 날 추천할 바로 그
동네들을 물리량으로 재현했다.

| 자료 | 밴드 | 해상도 | 쓰임 |
|---|---|---:|---|
| Landsat 8/9 C2 L2 | `lwir11` (ST_B10) | 30m | 지표면온도 — `DN × 0.00341802 + 149.0 K` |
| Sentinel-2 L2A | `B04`/`B08` | 10m | NDVI — 그늘·증발산의 대리 지표 |
| | `QA_PIXEL` / `SCL` | | 구름·그림자 마스킹 |

여름 한낮 장면 여러 장을 중앙값 합성하고 행정동 426개로 집계한다.
살려 둔 이유는 판정 사유에 그대로 적힌다 — *"폭염이지만 지표면온도가 서울
하위 22%인 우이동(32.1°C) — 실외 유지"*. 비는 동네를 가리지 않으므로 폭염일
때만 본다.

지도에서 바로 볼 수 있다. `지도 / 🛰 지표온도` 두 모드로 나눠 두었고, 열지도
모드에서는 행정동에 마우스를 올리면 그 동의 지표면온도·서울 내 순위·식생지수가
뜬다. 색은 **순차형이라 한 가지 색상**을 밝은 쪽에서 어두운 쪽으로 쓴다(무지개를
쓰면 중간 단계의 순서가 사라진다). 파랑은 '차갑다'로 읽히므로 주황 6단계이고,
단일 색상·단조 명도·단계 간격·표면 대비 검사를 통과한 값이다.

구간은 등간격이 아니라 **분위**로 나눈다. 등간격으로 자르면 서울 대부분이 맨 위
칸에 몰려 지도가 통째로 진해진다 — 분포가 더운 쪽으로 치우쳐 있기 때문이다.
대신 범례에 각 칸의 실제 온도 경계(40 · 41 · 42 · 43 · 44°C)를 적어 크기 정보를
잃지 않게 했다.

**키가 필요 없다.** Planetary Computer의 STAC과 SAS 토큰 발급이 모두 공개다.
결과(`data/dong_thermal.json`)가 저장소에 있어 앱을 쓰는 데는 이 모듈이
필요 없고, 근거를 재현하고 싶을 때만 돌린다.

```bash
python -m weatherfit.remote build     # 위성에서 새로 만든다 (약 10분)
python -m weatherfit.remote stats     # 만들어진 값 확인
```

## AI 도우미는 챗봇이 아니라 에이전트다

챗봇과 에이전트의 차이는 말투가 아니라 **행동**이다. 챗봇은 그럴듯한 문장을
만들고, 에이전트는 도구를 부르고 그 결과로 답한다. 그래서 순서를 뒤집었다.

1. **규칙이 도구를 확정적으로 돌린다** — 말 이해 → 위치 확인 → 취향 반영 →
   일정 구성 → 날씨 조회 → 위성 열지도 → 도보 실측
2. **LLM은 그 결과를 사람 말로 옮기기만 한다**

이 순서여야 둘이 보장된다. 키가 없어도 답이 나오고(도구는 그대로 돌고 문장만
템플릿이 된다), **LLM이 장소를 지어낼 수 없다**(답에 등장하는 모든 장소가
이미 판정을 통과한 실제 콘텐츠다). "갔는데 없더라"를 막는 게 이 앱의 전부인데
답변 생성기가 그걸 되살리면 안 된다.

답변에는 무엇을 했는지가 함께 붙는다.

```
어떻게 골랐는지 (6단계 · 규칙 문장)
  말 이해      폭염
  위치 확인    중구 명동 · 주변 848곳
  일정 구성    3곳 · 209분
  날씨 조회    폭염 35.0°C
  위성 열지도  지표면온도 상위 46% · 녹지 0.07
  도보 실측    3/3구간 실측
```

탭이 아니라 떠 있는 창이다(`Alt+A`). 지도를 보다가, 일정을 보다가 막히는
순간에 묻게 되므로 화면을 갈아치우면 안 된다.

## 트렌드 지능 — VITALITY를 잴 수 있는 것만 잰다

서울관광재단의 2026 관광 트렌드 분석은 여덟 글자다. 이걸 추천에 쓰려면 장소마다
숫자가 있어야 하는데, 재 보니 셋은 그렇게 할 수 없었다.

| 축 | 처리 | 왜 |
|---|---|---|
| Tailored Smart Travel | **서비스 축으로 분리** | 경복궁이 얼마나 개인화됐냐고 물으면 답이 없다 |
| Your Seoul | **서비스 축으로 분리** | 같은 곳이 누구에겐 나만의 서울이고 누구에겐 아니다 |
| Inclusive Choice | **뺐다** | 가격대·수용인원이 API에 없다. 행정동 다양성으로 대신했더니 상위가 전부 종로1·2·3·4가동 — '선택의 폭'이 아니라 '도심인가'를 재고 있었다 |

남은 다섯은 키워드로 지어내지 않고 **이미 재 둔 값에 연결한다.**

| 축 | 근거 | 상위 |
|---|---|---|
| 일상형 회복 | **위성 NDVI** | 용마산 스카이워크 · 매헌시민의숲 · 솔밭근린공원 |
| 안심의 흐름 | 무장애 항목 수(17.6%만 보유) · **서울시 살람서울 지정 152건** | 퐁피두센터 한화 · 서울시립 사진미술관 |
| 로컬 몰입 | **서울시 오래가게 지정 115건** | 거안 · 경인미술관 · 한상수자수박물관 |
| 콘텐츠 실감 | 전시·공연 소분류 | 전시 콘텐츠 |
| 감정 체류 | 야경·루프탑·한강뷰 태그 · 카페/찻집 | 63 스카이피크닉 · 불빛정원 · 서울라이트 DDP |

`살람서울`과 `오래가게`는 서울시가 직접 지정한 값이 태그에 들어 있다. 추측할
필요가 없다. 태그는 **정확 일치**로만 센다 — 부분 일치로 두었더니 `데이트코스`가
`데이트`에 걸려 전통공예명품전이 '감정 체류 0.85'가 됐다.

국적으로 취향을 추정하지 않는다. 트렌드 문서에 권역별 분석이 있지만 같은 나라
사람도 취향은 제각각이고, 국적으로 사람을 분류하는 화면은 좋게 읽히지 않는다.
대신 **여행 스타일 다섯 가지**를 본인이 고른다 — 어차피 더 정확하다.
시청 기준으로 다섯 스타일이 다섯 개의 서로 다른 코스를 만든다.

## 날씨가 바뀌어도 경험은 지킨다

지금까지의 재편성은 "비 오면 실외를 빼고 남은 것 중 점수 높은 곳"이었다. 그러면
'로컬 골목 산책 + 감성 카페'를 원했던 사람이 백화점을 받는다. 장소가 바뀌는 건
어쩔 수 없지만 **경험까지 바뀔 이유는 없다.**

`POST /api/replan`은 빠지는 자리마다 원래 그 자리에 있던 곳과 경험 좌표가 가장
비슷한 곳을 찾는다. 무엇을 무엇으로 바꿨는지 유사도와 함께 적는다.

```
비 (강수 4.0mm)로 남은 일정을 다시 짰습니다.
  성수동 유니온스타 볼링클럽 → 무신사 테라스 성수 (경험 유사도 86%)
  앤더슨씨 → 앤더슨씨 (그대로)
```

6개 지역 × 5개 스타일로 재 봤다. **평균 +2.7%p**인데, 스타일마다 다르다.

| 스타일 | 경험 보존 | 날씨만 | 차이 |
|---|---:|---:|---:|
| 분위기 좋은 곳 | 97.3% | 88.1% | **+9.2%p** |
| 편하고 안전하게 | 89.9% | 86.6% | +3.3%p |
| 동네 살아보기 | 91.0% | 88.9% | +2.1%p |
| 공연·전시 몰입 | 89.8% | 91.1% | −1.3%p |
| 쉬러 왔어요 | 79.2% | 79.2% | ±0.0%p |

**실내 대체가 있는 스타일에서만 이득이다.** 감성 카페는 실내 감성 카페로 바꿀 수
있지만 야외 녹지는 대체할 실내 녹지가 없다. 전시는 원래 실내라 비가 와도 코스가
거의 안 바뀌어서 차이가 나지 않는다. 그럴듯한 평균 하나로 뭉뚱그리지 않는다.

보존율은 **한 곳이 한 자리만 맡는 일대일**로 잰다. '새 일정 아무 곳과의 최대'로
재면 한 곳이 여러 자리를 덮어 무엇을 해도 90%가 넘는다.

## 인기 지표는 어디서 오나

흔히 기대하는 곳에 데이터가 없다([쓰지 않는 것](#쓰지-않는-것)). 남는 것이
위키백과다 — **키 없이 실측 조회수**를 주고, 문서가 있다는 것 자체가 신호다.

위키백과를 기본으로 쓴다. 문서가 없는 곳은 0이 아니라 품질 점수로 대신한다 —
0은 "유명하지 않다"가 아니라 "모른다"는 뜻이기 때문이다.

### 이름이 같다고 같은 곳이 아니다

이름으로만 문서를 붙였더니 매칭 786건 중 **494건(63%)이 다른 대상**이었다.

| 장소 | 붙은 문서 | 조회수 |
|---|---|---:|
| 히말라야 종각점 *(카레집)* | 히말라야산맥 | 11,700 |
| 버뮤다삼각지 *(술집)* | 버뮤다 삼각지대 | 29,140 |
| 에베레스트 영등포점 *(식당)* | 에베레스트산 | 9,676 |
| 제17회 국제차문화대전 | 제1차 세계 대전 | 10,070 |

세 겹으로 거른다.

1. **포함 매칭을 1.0으로 치지 않는다.** '히말라야'가 '히말라야산맥'에 들어
   있다는 사실은 신호이지 확신이 아니다. 길이 비율로 깎는다.
2. **문서 좌표와 장소 좌표의 거리를 본다.** 3km를 넘으면 다른 대상이다.
3. **식당·가게·숙소와 '○○점' 지점은 잣대를 높인다.** 이름이 겹치기 쉽고,
   정말 위키백과에 실린 가게라면 장소 문서라서 좌표가 있다.

검증은 지우지 않고 `geo_ok`로 표시만 한다. 다시 돌릴 수 있고 왜 뺐는지
확인할 수 있어야 하기 때문이다. `python -m weatherfit.popularity verify`.

거르고 나면 상위가 이렇게 바뀐다. 롯데월드타워 · 경복궁 · 청와대 ·
SM/YG/JYP엔터테인먼트 · 종묘 · 창덕궁 · 숭례문 · 국립중앙박물관.
8개 지역에서 8개의 서로 다른 일정이 나오고, 북촌은 경복궁·국립현대미술관,
이태원은 리움 미술관, 잠실은 롯데월드타워로 시작한다.

## 경로는 언제 실측하나

후보를 고르는 동안에는 추정만 쓴다. 한 자리에 여덟 곳을 시도하므로 시도마다
API를 부르면 일정 하나에 수십 번을 묻게 된다. 다 정해진 뒤 실제로 쓰는
서넛만 **동시에** 물어 실측으로 바꾸고, 밀린 시각으로 운영시간을 다시 본다.
실측이 추정보다 오래 걸려 뒤 일정이 안 들어가면 잘라 내고 그 사실을 적는다.

## 성능

3,802건 전수를 올린 상태에서 측정한 값(p50).

| 요청 | p50 | 크기 |
|---|---:|---:|
| `GET /` | 5.6ms | 10.4KB |
| 행정동 GeoJSON | 9.8ms | 1.1MB |
| `GET /api/where` | 7.7ms | — |
| `GET /api/candidates` | 46.0ms | 179KB |
| `POST /api/plan` | 67.3ms | 7.4KB |
| `POST /api/plan` (구간 실측, 첫 조회) | 0.3~0.7s | 7.4KB |
| `GET /api/stats` | 2.4ms | 캐시 |
| `POST /api/chat` | 21.2ms | 5.5KB |

정규화·행정동 매칭·인기도를 적재 시점에 한 번만 하기 때문이다. 요청마다
다시 파싱하던 초기 구현은 판정 한 번에 120ms, `/api/candidates`에 600ms가 들었다.

일정을 짤 때는 **거리로 먼저 자른다.** 반경 밖을 판정할 이유가 없는데도
3,802건 전부에 운영시간·날씨 판정을 돌리고 있었다. 거리 계산은 한 건에
마이크로초, 판정은 그보다 훨씬 비싸다. 순서를 바꾸니 일정 요청이 108ms에서
67ms로, 테스트 스위트 전체가 21초에서 7초로 줄었다.

측정 중에 실제 병목을 하나 찾았다. IPv4에만 바인드하면 브라우저가 `localhost`를
`::1`로 먼저 풀면서 폴백에 **2,038ms**가 걸린다. 반대로 IPv6에만 바인드하면
`127.0.0.1`이 끊긴다. `IPV6_V6ONLY`를 끈 듀얼스택 소켓 하나로 둘 다 받는다.

| 주소 | 전 | 후 |
|---|---:|---:|
| `localhost` | 2,038ms | **4.2ms** |
| `127.0.0.1` | 17ms | 17ms |
| `[::1]` | 연결 불가 | 2.1ms |

## 원문은 어디까지 기계가 읽을 수 있나

아래는 전부 이 코드가 실제로 잰 값이다. 전수 3,802건 기준.

| 항목 | 측정값 | 뜻 |
|---|---:|---|
| 운영시간이 규칙만으로 확정 | **22.9%** | 나머지 77.1%가 LLM 정규화의 몫 |
| └ 그중 요일 표기가 아예 없음 | **45.8%** | '매일'은 우리 가정이지 원문의 진술이 아니다 |
| 실내·실외 판정 불가 | **7.0%** | 소분류를 보기 전엔 24.8%였다 |
| 축제·행사 중 이미 종료 | **95.3%** | 목록 API에는 기간 필드가 없다 |
| 종료·휴무를 걸러내고 남는 것 | **48.6%** | 토요일 오후 2시 기준 |

원문 표기 하나를 못 읽으면 그대로 헛걸음이 된다. 덕수궁 왕궁수문장 교대의식의
이용시간은 `매일 3회 : 오전11시, 오후2시, 오후3시30분`이다. 콜론이 없어 파서가
놓쳤고, 그래서 "정보 없음 → 10~20시로 가정"이 적용돼 **10시 도착 일정에 들어갔다.**
회차 표기를 구간으로 바꾸고 나서는 11시·14시·15시30분에만 나온다.

`python -m weatherfit.report --at "2026-09-03 12:00"` 한 줄로 재현된다.

## 개인정보

취향 프로필은 **서버에 저장하지 않는다.** 화면이 들고 있다가 매 요청에 실어
보내고 서버는 그 요청에만 쓴다. 위치도 마찬가지로 브라우저 안에만 남는다.
개인화를 하면서 아무것도 쌓아 두지 않는 방법이다.
