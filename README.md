# 웨더핏 서울 (WeatherFit Seoul)

**오늘 날씨에, 지금 열려 있는 곳만 골라 짜는 AI 서울 코스**

2026 서울관광재단 비짓서울 API 데이터·AI 활용 아이디어 공모전 출품작.

서울을 찾은 외국인 관광객이 겪는 가장 흔한 실패는 코스가 시시한 것이 아니라
**갔는데 없는 것**이다. 이미 끝난 축제, 오늘 문을 닫은 가게, 비가 와서 못 하게
된 야외 일정. 웨더핏 서울은 비짓서울 API의 관광 콘텐츠에 *지금 갈 수 있는가*를
판정하는 계층을 얹어, 통과한 것만으로 시간표가 있는 반나절 일정을 만든다.

```
내 위치            →  마포구 서교동 · 주변 186곳
10:00부터 4시간
맑음 21°C

10:16–11:46  2027 S/S 서울패션위크   3일 뒤 끝납니다. 지금 아니면 놓칩니다
   ↓ 도보 6분 (추정)
11:53–12:53  뿌자2 인도 할랄 음식점   11:53 도착이면 식사 시간에 맞습니다
   ↓ 도보 4분
12:56–13:41  동대문 쇼핑타운
플랜 B  광화시장 — 날씨가 바뀌면 여기로
```

## 빠른 시작

```bash
pip install -r requirements.txt

python -m weatherfit.collect --all            # 콘텐츠 수집 (약 20분)
python -m weatherfit.popularity build         # 인기도 캐시 (약 25분, 선택)
python -m weatherfit.server                   # http://127.0.0.1:8020
```

행정동 경계(`web/data/seoul_dong.geojson`)는 저장소에 포함돼 있어 바로 지도가 뜬다.

## 무엇으로 고르는가

거리만 보면 약국이 오고, 품질만 보면 반대편 동네 명소가 온다. 인기만 보면
유명한 곳만 돌게 되고, 취향만 보면 늘 같은 것만 본다. 넷을 섞는다.

| 축 | 비중 | 무엇을 보나 |
|---|---:|---|
| 거리 | 30% | 2km를 0점 기준으로 한 근접도 |
| 품질 | 25% | 설명 길이·태그·홈페이지·무장애 정보·운영시간 신뢰도 |
| 인기 | 25% | 위키백과 문서 유무와 월별 조회수 (+구글 평점, 있으면) |
| 취향 | 20% | 말한 관심사 · 좋아요 · 관심없음으로 학습한 태그 벡터 |

여기에 **다양성 상한**을 건다. 반나절에 식당 네 곳은 일정이 아니다.
대분류 최대 2곳, 소분류 최대 1곳. 약국·편의점·관광안내소·물품보관소는
일정에서 빼되 주변 목록에는 남긴다 — 약이 필요한 순간도 있다.

## 인기 지표는 어디서 오나

흔히 기대하는 곳에 데이터가 없다. 정직하게 적어 둔다.

| 출처 | 평점 | 비고 |
|---|---|---|
| 카카오맵 로컬 API | **없음** | 이름·주소·좌표·카테고리만. 평점은 웹에만 있고 크롤링은 약관 위반 |
| 네이버 지역 검색 | **없음** | 데이터랩 트렌드는 상대 검색량을 준다 |
| 구글 Places | 있음 | 평점·리뷰 수. 과금 계정 필요 |
| **위키백과** | — | **키 없이 실측 조회수.** 문서가 있다는 것 자체가 신호 |

위키백과를 기본으로 쓴다. 롯데월드타워 14,191 · 경복궁 9,266 · 리움 493(3개월).
문서가 없는 곳은 0이 아니라 품질 점수로 대신한다 — 0은 "유명하지 않다"가 아니라
"모른다"는 뜻이기 때문이다.

## API 키

**하나도 없어도 전부 동작한다.** 없으면 무엇으로 떨어지는지는 `/api/health`와
화면에 항상 표시된다. `.env.example` 참고.

| 변수 | 없을 때 |
|---|---|
| `VISITSEOUL_API_KEY` | 공개 카탈로그를 소스로 수집 |
| `KMA_API_KEY` | 맑음 21°C 기본값으로 판정 |
| `TMAP_APP_KEY` | 도보 시간을 직선거리 × 1.3으로 추정 |
| `ODSAY_API_KEY` | 대중교통 시간을 평균속도로 추정 |
| `NAVER_CLIENT_ID`/`SECRET` | 자동차 시간을 직선거리로 추정 |
| `KAKAO_REST_KEY` | 카카오 등재 확인을 건너뜀 |
| `GOOGLE_PLACES_KEY` | 평점 없이 위키 조회수만 |
| `ANTHROPIC_API_KEY` | 규칙 기반 의도 파악·템플릿 답변 |

각 구간의 소요시간에는 **실측인지 추정인지**가 함께 표시된다.

## 이 저장소가 증명하는 것

제출물은 3장짜리 문서이고 데모 심사가 없다. 그래서 이 코드는 제품이 아니라
**제안서의 주장을 실측으로 뒷받침하기 위한 것**이다. 전수 3,788건 기준.

| 항목 | 측정값 | 뜻 |
|---|---:|---|
| 운영시간이 규칙만으로 확정 | **21.7%** | 나머지 78.3%가 LLM 정규화의 몫 |
| └ 그중 요일 표기가 아예 없음 | **45.7%** | '매일'은 우리 가정이지 원문의 진술이 아니다 |
| 실내·실외 판정 불가 | **6.9%** | 소분류를 보기 전엔 24.8%였다 |
| 축제·행사 중 이미 종료 | **99.2%** | 목록 API에는 기간 필드가 없다 |

`python -m weatherfit.report --at "2026-09-03 12:00"` 한 줄로 재현된다.

## 구조

```
weatherfit/
  models.py      Content 도메인 모델, 카테고리·어권 코드
  sources/       catalog(공개 HTML) · api(공식 API) — 같은 인터페이스
  collect.py     수집 CLI. cid 기준으로 재개 가능
  normalize.py   자유 문장 운영시간 → 구조화 시간표, 실내외 태깅
  index.py       적재 시점 1회 정규화 + 행정동 매칭 + 번역 병합
  validate.py    기간·날씨·운영 판정. 탈락과 판정불가를 구분
  quality.py     관광지 품질·다양성 상한·랭킹
  popularity.py  위키/카카오/구글/네이버 인기 지표 (배치 캐시)
  taste.py       관심사 학습. 태그 벡터와 친화도
  routing.py     TMAP 보행 · ODsay 대중교통 · 네이버 자동차
  course.py      시간표가 있는 일정 구성
  chat.py        대화형 의도 추출과 답변 생성
  weather.py     기상청 초단기실황 (격자 변환 포함)
  llm.py         LLM 호출 어댑터. 없으면 규칙으로 폴백
  geo.py         행정동 경계 추출·좌표 매칭
  report.py      근거 수치 리포트
  server.py      FastAPI + 정적 파일
web/
  index.html     지도 위에 유리판을 얹은 단일 화면
  app.js         Leaflet, 위치·일정·대화·주변·근거
  style.css      밝은 낮의 서울 — 글라스모피즘
  vendor/        Leaflet (CDN 의존을 없애기 위해 동봉)
tests/           95개. 실제로 났던 회귀를 그대로 박아 둔다
```

자세한 설계 판단은 [ARCHITECTURE.md](ARCHITECTURE.md).

## 엔드포인트

| 경로 | 하는 일 |
|---|---|
| `GET /api/health` | 적재 건수, 키 보유 여부, 사용 가능 어권 |
| `GET /api/where` | 좌표 → 행정동 (외부 API 없이 자체 경계로) |
| `GET /api/weather` | 현재 기상 (`mode=auto\|clear\|rain\|heat`) |
| `GET /api/candidates` | 판정 결과가 붙은 주변 목록 |
| `POST /api/plan` | 취향을 반영한 일정 |
| `GET /api/course` | 취향 없는 단순 일정 |
| `GET /api/routing` | 두 지점 사이 도보·대중교통 소요시간 |
| `GET /api/stats` | 근거 수치 + 자치구 분포 |
| `POST /api/chat` | 대화 한 턴 → 답변 + 일정 + 의도 + 취향 |

## 개인정보

취향 프로필은 **서버에 저장하지 않는다.** 화면이 들고 있다가 매 요청에 실어
보내고 서버는 그 요청에만 쓴다. 위치도 마찬가지로 브라우저 안에만 남는다.
개인화를 하면서 아무것도 쌓아 두지 않는 방법이다.
