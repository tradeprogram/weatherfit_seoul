# 제안서 문장 ↔ 코드 대응표

공모전 제안서에 쓴 주장 하나하나가 어느 코드에서 나온 수치인지 적어 둔다.
심사에서 "이 숫자 어디서 나왔냐"는 질문이 오면 이 표를 보면 된다.
모든 수치는 아래 한 줄로 재현된다.

```bash
python -m weatherfit.report --at "2026-09-02 14:00"
```

## 배경 (2) — 데이터 분포

공개 카탈로그의 `총 N건` 표기를 그대로 읽는다.

| 음식 | 1,259 | 33.2% |
| 축제/공연/행사 | 1,194 | 31.5% |
| 문화관광 | 739 | 19.5% |

| 역사관광 | 88 | 2.3% |
| 자연관광 | 71 | 1.9% |

한국어 3,788건 기준. 어권별로는 ko 3,788 / en 3,763 / ja 3,546 / zh-CN 3,535 /
zh-TW 3,509 / ru 1,370 / ms 881.

## 배경 (3) 시의성 공백

> 축제·공연·행사 1,194건을 전수 조사한 결과, 기간이 표기된 1,145건 중
> 1,136건(99.2%)이 이미 종료된 행사였다

처음에는 100건 표본으로 93%를 얻었고, 전수 조사에서 **99.2%**로 더 나빠졌다.
표본이 아니라 전수라는 점이 이 수치의 힘이다. 판정 코드는
`weatherfit/validate.py:check_period`.

> 콘텐츠 목록 조회 API의 응답에는 행사 기간(schdul_info) 필드가 포함되지 않아

API 문서의 응답 필드 목록으로 확인. `weatherfit/sources/api.py`가 목록→상세
2단계로 짜여 있는 이유가 이것이다. 상세 조회에서만 `schdul_info_bgnde/endde`,
`map_position_x/y`, `cmmn_use_time`, `closed_days`, `subway_info`가 나온다.

## 배경 (3) 비정형 운영정보

> 표기가 제각각이고 한국의 공휴일 규칙이 문장에 섞여 있어

`weatherfit/normalize.py:parse_hours`가 신뢰도 3단계로 분류한 결과가 근거다.

| 등급 | 뜻 | 제안서에서의 쓰임 |
|---|---|---|
| `high` | 요일·시각 모두 명시 | "규칙만으로 확정되는 비율" |
| `low` | 예외 단서 있음, 또는 요일을 가정 | LLM이 담당할 몫 |
| `none` | 시각 패턴 없음 | LLM이 담당할 몫 |

테스트 `tests/test_normalize.py`가 실제 콘텐츠 문자열로 이 등급이 정직한지
검증한다. 파싱이 된 것처럼 보이지만 사실은 가정을 얹은 경우를 `high`로
올리지 않는 것이 핵심이다.

## 세부 내용 [A] — 실내/실외 태깅

> post_desc·tag·cate_depth를 근거로 한 실내/실외/반실내 태깅.
> API에 존재하지 않는 필드를 AI가 새로 생성하는 것

`weatherfit/normalize.py:tag_environment`. 규칙 기반으로 남는 `unknown` 비율이
곧 LLM 태깅이 담당해야 할 범위다.

주의: 초기 구현에서 실내 키워드에 `관` 한 글자를 넣었더니 "경복궁 수문장
교대의식"까지 실내로 분류됐다. 키워드를 구체화해 전수 기준 `unknown`이
**24.8%(940건)**로 내려왔다. **규칙을 정교화하면 줄어드는 구간과, 그래도 남는 구간이 나뉜다는 것
자체가 LLM 필요성의 근거**다.

## 세부 내용 [B] — 웨더핏 판정

> 종료된 행사 제외, 오늘 휴무 제외, 강수·폭염·한파 시 실외 제외

`weatherfit/validate.py:evaluate`. 기간 → 날씨 → 운영 순으로 건다.

여기서 제안서에 쓰지 않았지만 중요한 설계 판단이 하나 있다. **탈락과 판정
불가를 구분한다.** 정보가 없어서 모르는 것을 "열려 있다"로 처리하면 헛걸음이
생기고, "닫혔다"로 처리하면 멀쩡한 후보가 사라진다. 화면의 「근거」 탭이 그
비율을 그대로 보여 준다.

## 세부 내용 [C] — 코스 구성

> 오늘의 행사 1곳 + 도보권 로컬 음식 1~2곳 + 날씨 급변 대비 실내 대안 1곳

`weatherfit/course.py:build_course`. 가까운 순이 아니라 종료 임박 순으로
앵커를 고른다.

실데이터에서 걸린 함정: 식당이 영업기간을 `2026.01.01~12.31`로 적어 두는
경우가 많아, 기간이 있다는 것만으로 행사로 보면 식당이 앵커가 된다.
90일 이하만 행사로 본다(`Content.is_short_event`).

## 실현 가능성

> 비짓서울 API와 기상청 단기예보 API 두 가지면 핵심 기능이 성립한다

`weatherfit/weather.py`가 기상청 초단기실황을 부른다. 위경도 → 기상청 격자
변환(LCC)까지 구현돼 있다. 키가 없으면 기본값으로 떨어지되 `source="fallback"`
으로 표시한다.

> 한국어 3,788건은 소규모 팀이 전량 정규화할 수 있는 크기

`python -m weatherfit.collect --all`로 실제로 전량 수집했다. 8개 카테고리
합계가 카탈로그 총계 3,788건과 정확히 일치한다. 공개 카탈로그 기준
요청당 0.35초 간격으로 약 20분.

## 발전 방향 — 관광 분산 지표

> 추천 결과가 실제로 어느 자치구에 분포했는지 집계해

`weatherfit/geo.py:assign_dong`이 콘텐츠 좌표를 행정동에 공간 조인한다.
통계청 행정동 경계에서 서울 426개(25개 자치구)를 뽑아 쓴다.
`/api/stats`의 `distribution`이 기준선이고, 추천 결과 분포가 이보다 고르면
분산 효과가 있다고 본다.

## 발전 방향 — 무장애 관광

> disabled_facility(엘리베이터, 장애인화장실, 휠체어 대여 등)를 필터로 노출

상세 조회에 실제로 들어 있는 배열 필드다. `Content.accessibility`로 수집하고
있으며, 화면 상세 패널에 이미 표시된다. 필터 UI만 붙이면 된다.
